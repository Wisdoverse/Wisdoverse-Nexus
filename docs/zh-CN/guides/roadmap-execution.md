# 路线图执行标准

本指南通过范围明确的工作包、责任、量化门槛和可复现证据，把[路线图](../roadmap.md)
转化为执行计划。适用于项目已说明的评估范围内、计划中的 M1–M5 能力。
[英文指南](../../en/guides/roadmap-execution.md)是主版本，两种语言保持相同规则。

## 当前基础与计划门槛

以下数值均为**等待验证的 Nexus 拟定目标**。实测值、实际负责人和完成证据在工作项中记录前，
均保持未指定状态。公开工程实践用于指导流程；这些数字是项目自己的选择，不构成公司认证或 SLA。

| 领域 | 仓库当前检查 | 计划增加的检查 |
| --- | --- | --- |
| 构建与正确性 | Rust 格式/Clippy/工作区测试、移动端检查、Web/SDK/文档构建及 M1 真实网关与浏览器检查 | 随支持范围扩展验收契约与配置 |
| 覆盖率 | CI 中工作区行覆盖率下限为 60% | 保留下限；为认证、租户、工具/批准和持久化路径增加至少 80% 的变更可执行行覆盖率，并要求关键行为测试（RD-004、RD-008、RD-012） |
| 安全 | 依赖/公告、许可证、密钥、CodeQL 和容器检查 | 权限撤销、上下文泄露、提示注入和副作用批准测试（RD-005、RD-007、RD-010、RD-015） |
| 性能 | 已有 benchmark 入口和通用网关指标 | 版本化端到端负载配置、SLI 测量、预算和回归门槛（RD-008、RD-012） |
| 发布 | 按 tag 触发的容器/SDK 工作流、容器 SBOM/provenance 配置 | 验证发布产物、验收证据、升级/恢复和分阶段启用（RD-011、RD-012、RD-016、RD-020） |

新增门槛在相应测量和 CI 工作落地后才实际执行。覆盖率不能替代可观察的行为检查。
确认每个必测场景都有 CI 可执行的测试目标；仅存在测试文件不足以证明它已被执行。
新增检查时保留现有检查。已审阅的安全公告例外应记录责任角色、原因、缓解措施，
以及到期时间或重新检查上游的条件。

## 工作项生命周期

使用[路线图工作项模板](https://github.com/Wisdoverse/Wisdoverse-Nexus/blob/main/.github/ISSUE_TEMPLATE/roadmap_work_item.md)
记录 Planned（计划中）→ Ready（可开始）→ In progress（进行中）→ In review（审阅中）
→ Validated（已验证）→ Released（已发布）。Blocked（阻塞）状态记录依赖或失败门槛及下一步。
Validated 表示指定提交已通过约定验收；Released 还需要发布产物验证及适用的启用检查。

进入 Ready 前记录：

- 用户/运维结果、范围、非目标、依赖 ID、DRI、审阅者和受影响的 DDD/FSD 边界。
- 契约示例，以及相关身份、schema/协议变更、数据流、权限、兼容性和迁移的设计决定。
- 可复现验证计划，包含正常、拒绝、失败及恢复场景；写明配置、目标、测量窗口和预期结果。
- 对运行中服务或持久状态有影响的变更，记录资源/token/费用预算、运维风险和回滚或禁用策略。

进入 Validated 前记录：

- 已审阅 PR 和提交、通过的适用必需检查、可独立复现的行为证据。
  按变更影响确定验证范围：文档检查构建/链接，行为变更需要适当回归测试。
- 更新后的契约、客户端/SDK 示例、changelog 和迁移说明。
- 与受影响运行/数据路径匹配的运维信号、失败处理和演练证据。
- 实测门槛值和未解决风险。调整目标需记录版本化理由并重新评估，保留之前的失败证据。

## 验收配置 QP-1

QP-1 面向首条支持的单节点评估路径。运行前固定提交、release 构建、feature flag、
持久化后端、数据集、客户端版本、命令和主机/存储/网络条件。
网关独享 **2 vCPU、4 GiB RAM**；若另用数据库，单独记录其资源。
其他硬件或多节点运行需要独立的目标和证据。

负载为 **10 个房间中的 100 个 WebSocket 客户端**、总计 **50 条消息/秒**、
**1 KiB 载荷**，通过认证后的 HTTP 消息写入发送，再加 **20 次 HTTP 房间/消息读取/秒**，
总计 **70 次 HTTP 请求/秒（50 次写入 / 20 次读取）**。
在说明的本地网络中测量客户端观察到的延迟，外部模型/工具延迟单独统计。
预热 5 分钟后测量 30 分钟，重复三次，每次都必须通过门槛。
公开样本数、错误、p50/p95/p99、RSS 峰值、CPU 和配置。
成功响应延迟与失败/超时请求一起报告，失败计入 QG-03；超出此负载时，以有界队列和明确背压安全拒绝。

| 门槛 | 拟定目标 | 必需证据 / 阶段 |
| --- | --- | --- |
| QG-01：契约正确性 | 必测正常/拒绝场景 100% 通过 | 真实网关客户端/SDK 报告；M1 起 |
| QG-02：传输延迟 | HTTP p95 ≤200 ms、p99 ≤500 ms；WS 发送到接收端 p95 ≤500 ms | QP-1 客户端采样，包含失败计数；M3 |
| QG-03：网关成功率 | ≥99.9% 的有效 HTTP 请求在 2 秒内返回预期成功响应 | QP-1 报告及下述 SLI 定义；M3 |
| QG-04：状态安全 | 进程崩溃/重启后已确认写入零丢失；同一重试键在声明窗口内零重复副作用 | 故障注入报告和持久确认契约；M3/M4 |
| QG-05：资源稳定性 | 网关 RSS 峰值 ≤2 GiB；预热后工作集有界的 24 小时持续运行中，末 6 小时 RSS 中位数 ≤首 6 小时中位数的 110% | QP-1 限额、声明的留存/工作集、内存序列和队列限制；M3 |
| QG-06：恢复 | 备份 RPO ≤24 小时，恢复 RTO ≤30 分钟 | 模拟存储丢失，恢复 10 个房间/10,000 条消息及启用的产物，直到客户端冒烟检查通过；M3/M4 |
| QG-07：授权 | 必测场景中跨房间/租户泄露、未授权工具调用及未批准副作用均为零 | 拒绝、权限撤销和对抗场景结果；M2 起 |

QG-04 适用于持久存储仍完好时，进程崩溃前已确认的写入。
QG-06 适用于存储丢失后，从定时备份恢复；记录备份的一致性边界及实际产物数量。
一次成功演练或持续运行测试不足以证明更长时间窗口的可用性。

### SLI 与错误预算策略

网关 SLI = 良好有效请求数 / 全部有效请求数。
有效请求是在声明负载内，对支持的房间/消息端点发起的、认证通过的合法调用。
良好请求在 2 秒内返回预期成功响应。服务端错误、依赖失败、超时和非预期限流计为不良事件。
预期的权限拒绝和格式错误请求单独报告，并有独立安全断言。
外部 AI/工具的成功率和延迟单独报告，包含提供商失败和取消。

拟定运维目标为**滚动 30 天窗口内 99.9%**，允许错误预算为**有效请求的 0.1%**。
RD-012 落实分母和失败分类测量后，再实际执行该策略。
30 分钟负载或 24 小时持续运行只证明相应窗口的验收结果；
30 天目标需要该窗口内真实的运维遥测。

候选预算消耗速率告警用不良事件比例除以 0.001：快速告警要求 1 小时及 5 分钟窗口均 ≥14.4 倍；
慢速告警要求 6 小时及 30 分钟窗口均 ≥6 倍。每个告警窗口至少有 100 个有效事件；
否则标记数据不足，并保留合成健康检查。无论流量多少，数据丢失和权限违规都会停止扩大启用范围。
运维错误预算耗尽时，优先修复可靠性问题并暂停功能推广，直到负责人记录恢复和新的评估。

## AI 质量与产品评测

RD-008 为 **50 个合成场景**记录版本、预期行为和评分规则：

| 场景类别 | 数量 | 预期结果 |
| --- | --- | --- |
| 有依据的正常房间/文档问答 | 25 | 回答相关、来源引用正确、不声称执行未经证实的操作 |
| 跨房间/租户访问及权限撤销 | 10 | 拒绝，且无泄露或副作用 |
| 消息或工具输出中的提示注入 | 5 | 保持策略和工具范围 |
| 提供商/工具超时、重试及取消 | 5 | 终态正确、重试有界，确认取消后不再继续执行 |
| 预算耗尽和需要批准的操作 | 5 | 到达限制即停止；写入必须有记录的人类批准 |

M2 的有依据问答使用房间消息，写入请求按只读范围必须被拒绝。
到 M4 再将版本化场景扩展到有权访问的文档/会议记录和已批准写入/权限撤销，
保持各类场景数量并重新出具报告。

固定模型/提供商配置、prompt/上下文版本、工具 schema、场景提交和评分规则。
重复三次：正常回答整体至少 90% 通过评分规则，缺失或失败的正常回答计为失败；
每次重复中，所有安全/失败场景都必须达到约定的安全结果。
记录分歧和审阅者判断。允许的失败必须可观察且安全，不能静默显示成功。
CI 使用确定性提供商；真实提供商验收采用可选运行、运行时凭据，单独报告费用和数据外发。

拟定单次执行初始限制为 **60 秒、4 次工具调用、4,096 个输出 token**；
进入 Ready 前记录提供商/工具超时及租户并发限制。
服务端在预算耗尽或取消确认后，必须阻止后续执行。记录 token 用量和带日期的模型计价假设，
付费试用前设置金额预算。需要其他限制的集成必须采用已审阅配置并重新验证。

RD-016 还需由至少 **5 位自愿评估者完成 50 次范围明确的工作流尝试**，
目标为**正常工作流完成率 ≥90%**。一起报告开始、完成、拒绝、取消及失败数量，分母包含提供商失败。
公开匿名结果和限制，避免个人身份与私有内容。
检查关键 Web/移动端流程的键盘/焦点行为、无障碍标签及状态播报，并记录浏览器/设备兼容性。

## 发布门槛与证据

| 阶段 | 进入证据 | 扩大范围 / 停止条件 |
| --- | --- | --- |
| 可信 alpha | M1/M2 验收、QG-01/QG-07、固定提供商/工具范围、已测试的 Agent 禁用路径 | 从合成房间到一个自愿试用工作空间；任何策略违规都禁用受影响的 Agent/工具执行 |
| 评估 beta | M3、一条 M4 流程、QP-1/AI/试用报告、恢复演练和运维手册 | 在已验证容量内扩大范围，每次分阶段启用观察至少 24 小时；门槛失败暂停扩大范围 |
| 1.0 候选 | 全部支持路径的验收、兼容/迁移策略、产物验证、剩余风险处理和发布就绪审阅 | 只发布有证据的支持矩阵；未支持的 M5/联邦/媒体路径保留实验状态 |

采用适合已验证单节点路径的分阶段功能启用。每次扩大范围前检查指标、未解决事件、预算和数据完整性。
失败时禁用功能或恢复已知正常产物；使用旧二进制前，验证 schema 兼容性或恢复路径。
在验收数据集副本上演练回滚，并记录实测恢复时间。

证据包包含提交/tag、镜像/软件包摘要及版本、支持配置、门槛 ID、目标与实测值、样本量、
CI/测试 URL、审阅者/DRI、例外处理和启用/恢复结果。验证发布镜像和 SDK 的全新安装。
已配置的 SBOM/provenance 工作流只有实际生成可验证产物后才可标记完成，
签名 provenance、产物身份和源码提交应相互关联。

门槛记录使用机器可读报告，例如：

```json
{
  "schema_version": 1,
  "work_item": "RD-012",
  "status": "planned",
  "commit_sha": null,
  "profile": "QP-1",
  "gate": "QG-02",
  "target": {"http_p95_ms": 200, "http_p99_ms": 500},
  "observed": null,
  "sample_count": null,
  "evidence_url": null,
  "dri": null,
  "reviewer": null
}
```

证据字段为空，避免把计划报告当作通过。报告范围限定为实际测试的提交、环境和配置。

## 风险与审阅节奏

| 风险 | 首要缓解措施 / 责任角色 |
| --- | --- |
| HTTP/WS/客户端/SDK 契约漂移 | 版本化样例和真实网关 CI；协议 / 测试基础设施 |
| AI 上下文泄露或未授权副作用 | 上下文 ACL、执行时授权、批准和禁用控制；AI / 安全 |
| 崩溃丢失、schema 迁移或索引过期 | 持久确认契约、恢复演练、生命周期检查；存储 / 平台 |
| 提供商中断、延迟或费用上升 | 硬预算、取消、明确失败状态和已验证提供商矩阵；AI 评测 |
| 范围膨胀和未经验证的部署声明 | 明确关键路径和验收配置；路线图 DRI |

开始实现后，每周审阅活跃工作和阻塞项。每个里程碑退出时审阅目标、试用反馈和容量，并更新两种语言。
通过范围明确的 PR 记录变化。事件复盘使用脱敏证据，记录原因、检测/恢复缺口和有负责人的后续事项。
